# Deploying Sukuu

Three services, chosen so that no single free tier can quietly kill the demo:

| Piece | Where | Why |
|---|---|---|
| Frontend | Vercel | Static build; its home ground |
| API | Render | A long-lived process, so SQLAlchemy's own pool works as designed and migrations get a release step |
| Postgres | Supabase | Render's free Postgres **expires after 30 days** and is then deleted — the "empty demo the week someone looks" the roadmap warns about |

Both hosts default to **Python 3.14**, so the roadmap's "or drop to 3.13" never had to happen.

---

## 1. Supabase — the database

Create a project, then take the connection string from **Connect → Session pooler**.

Two details that matter more than they look:

- **Session mode, not transaction mode.** The API is a long-lived process with its
  own connection pool. Session mode behaves like a direct connection, which is what
  `SELECT … FOR UPDATE` and psycopg's prepared statements both want. Transaction-mode
  pooling multiplexes connections between statements and can break prepared statements.
- **The pooler host, not the direct one.** Direct connections are IPv6-only unless you
  pay for the IPv4 add-on, and outbound IPv6 is not something to assume of a host.

Rewrite the scheme for SQLAlchemy — Supabase gives you `postgresql://`, this project
uses psycopg 3:

```
postgresql+psycopg://postgres.<ref>:<password>@<pooler-host>:5432/postgres
```

## 2. Migrate and seed, from your laptop

Free Render instances have **no shell access**, so this cannot be done on the server.
It does not need to be — Supabase is reachable from anywhere.

```bash
cd backend
DATABASE_URL='<the session-pooler URL>' .venv/bin/alembic upgrade head
```

```bash
cd backend
DATABASE_URL='<the session-pooler URL>' .venv/bin/python -m app.db.seed
```

The seed is idempotent: it checks for an existing student and stops rather than
doubling the data.

## 3. Render — the API

Point Render at this repo; `render.yaml` at the root describes the service. Fill in
the values marked `sync: false`:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the session-pooler URL from step 1 |
| `FRONTEND_ORIGIN` | the Vercel URL from step 4 — set it after, then redeploy |
| `STRIPE_SECRET_KEY` | `sk_test_…` from the Stripe dashboard |
| `STRIPE_WEBHOOK_SECRET` | from step 5, **not** the one `stripe listen` printed |
| `STRIPE_SUCCESS_URL` | `https://<vercel-app>/payments/success` |
| `STRIPE_CANCEL_URL` | `https://<vercel-app>/payments/cancelled` |

`JWT_SECRET` is generated by Render. Do not reuse the local one.

Migrations run as `preDeployCommand`, after a successful build and before the new
version takes traffic. Deliberately not in the build step: a build can run for a
preview or be retried, and would migrate whatever database it happened to point at.

**Free instances spin down after 15 minutes of inactivity** and take about a minute
to wake. Consequences worth knowing rather than discovering:

- The first visit after a quiet period is slow. The login page says so.
- A Stripe webhook arriving at a sleeping service may time out — and then be retried,
  and land, because the webhook is idempotent on `stripe_event_id`. Phase 5 paying off.

## 4. Vercel — the frontend

Import the repo, set the root directory to `frontend`. `vercel.json` handles the rest,
including the rewrite that makes a hard refresh on `/students` serve the app rather
than a 404.

One environment variable:

```
VITE_API_URL=https://<render-service>.onrender.com
```

Then go back to Render, set `FRONTEND_ORIGIN` to the Vercel URL, and redeploy. The API
**refuses to start** if that value is a wildcard, so a misconfigured deploy fails
loudly instead of leaving the API open to every origin.

## 5. Stripe — the webhook

Add an endpoint in the Stripe dashboard (test mode) pointing at:

```
https://<render-service>.onrender.com/webhooks/stripe
```

Subscribe to `checkout.session.completed`, `checkout.session.expired`, and
`payment_intent.payment_failed`. Copy that endpoint's signing secret into Render as
`STRIPE_WEBHOOK_SECRET`.

This is a **different secret** from the one `stripe listen` printed locally. Using the
local one means every real delivery fails signature verification, which looks like a
code problem and is not.

## 6. Smoke test

Nothing here is a substitute for the loop actually working:

1. Sign in as all three demo logins.
2. As the bursar, record a cash payment; check the balance moves.
3. As a parent, pay a fee with card `4242 4242 4242 4242`.
4. Confirm the payment appears in the parent's history — that proves the webhook
   arrived, was verified, and was recorded, which is the only thing that does.
5. Check the audit trail: `payment.stripe` with the Stripe event id in its detail.

## What a stranger can and cannot do

The demo logins are public, so assume they will be used.

**There are no delete endpoints in this API at all.** Classes archive, students go
inactive, fee types cannot be removed. Nothing a visitor does destroys data.

They can still create classes, enrol students, and record payments, so the demo
accumulates noise. Reseeding on a schedule is the roadmap's suggestion and remains
the honest answer; the seed script's guard means it will not run against a database
that still has students, so a reset needs the data dropped first.
